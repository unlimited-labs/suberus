# Research: Hatchet as a replacement for pg-boss

Issue: unlimited-labs/suberus#130 (map #124). Date: 2026-11-08. Code read at `c5ee64b2` (branch base; `origin/master` `ad8ab70f` adds only a planner UI fix).

Builds on #125 (`research/shared-job-broker`, `dev-docs/research/shared-job-broker.md`). Not repeated here: the Shared-service call-site table, the broker candidate ranking (Hatchet first if a broker is ever needed), and the in-service admission-queue baseline. This note answers the narrower question: can Hatchet replace pg-boss for **all** background work, and should it front the Shared services.

## Verdict: not now

- **Do not replace pg-boss for Instance-internal work.** Every pg-boss job needs the Instance's own DB, S3 bucket and SMTP, so the workers stay in each Instance app whatever the transport. Hatchet would only swap the transport. In exchange it adds one cross-Instance failure domain (today each queue lives in its Instance's DB), a fourth shared stateful service on jack, an E2E dependency, and a pre-1.0 engine that ships about 1.5 minor versions a week. Volume is tiny: the busiest Instance has created 88 tracked jobs since June 2026 (prod query, below). None of Hatchet's strengths (throughput, durable DAGs, dashboard) applies at that volume.
- **Do not put it in front of the Shared services yet either.** #125's reasons still hold (one host, 1 replica, bounded fan-in, MB-sized bytes, P12 at rest). This note adds three findings that make Hatchet worse than #125 assumed:
  1. **Isolation and fairness exclude each other.** API tokens are bound to one tenant, and priority and concurrency apply only inside one tenant. So a tenant per Instance gives isolation but no cross-Instance priority or fair share. One shared tenant gives fair share, but every Instance's token can then read, cancel and replay every other Instance's runs and payloads.
  2. **Hatchet would crowd the shared Postgres.** An idle `hatchet-lite` v0.119.2 holds **25–31 connections**. jack's `srv-shared-postgres` has `max_connections = 100`, with 35 in use by 4 Instances plus other projects.
  3. **Fair-share bugs are still open:** round-robin over-admission #4778 and concurrency released during retry backoff #5254.
- **When to revisit:** use #125's triggers (multi-host or several replicas per Shared service, interactive jobs that must survive a restart, fan-in beyond what admission absorbs). Then the shape is **Hatchet for Shared-service work only**: one tenant, Instance key in `additional_metadata`, claim-check bytes through MinIO, own DB with a capped pool, engine upgraded before Instances. pg-boss stays inside the Instances.

## 1. pg-boss today and the Hatchet equivalent

Core: `src/shared/server/queue.ts`. `new PgBoss({ connectionString: env.DATABASE_URL, monitorIntervalSeconds: 30 })`, so the pg-boss schema sits in the **Instance's own DB**. It `createQueue`s the 6 queues and lazily imports `src/pg-boss-workers.ts`, which registers 6 `boss.work` handlers. The singleton is kept on `globalThis.__pgBoss`. Boot: the nitro plugin `src/server/plugins/pg-boss.ts` calls `getBoss()`. The plugin and the request path load separate copies of `queue.ts`, so the `globalThis` slot keeps it to one boss, and workers run from the nitro-bundle copy of feature modules. The single send path is `ensureQueueAndSend(name, data, {retryLimit, retryDelay, expireInSeconds, startAfter})`.

Not used anywhere in `src/`: `singletonKey`, `boss.schedule` (cron), `priority`, `group`, transactional send, job ids. Grep: `pg-boss|PgBoss|boss\.(send|work|schedule|createQueue)|startAfter|singletonKey`. Cron lives in **nitro `scheduledTasks`** (`vite.config.ts`: `program:reminders` every minute, `mails:reminder`/`assignments:overdue`/`services:health` every 5 min, `cas:reaper` 03:30), not in pg-boss. Progress and results live in the app table `job_progress`, not in pg-boss.

Scheduled send does not store pg-boss job ids. A cancel flips the row to DRAFT. The worker claims with `updateMany … where scheduledAt = payload.scheduledAt`, which neutralises stale jobs after a cancel or reschedule. This design is transport-agnostic and ports unchanged.

E2E: `playwright.config.ts` gives each Playwright worker its own DB `suberus_e2e_${i}` and server port. pg-boss lives in that DB, so queue isolation per worker costs nothing and resets with the DB. Specs that drive jobs end to end: `e2e/extraction/*`, `e2e/admin/bulk-email*.spec.ts`, `announcements.spec.ts`, `planner/autoplan-queue.spec.ts`, `workflows/revision-metadata.spec.ts`.

## 2. Isolation

- A tenant is "a separate environment with its own set of workflows and workers" ([environments](https://docs.hatchet.run/v1/environments)). "API tokens authenticate workers and applications with a single Hatchet tenant" ([API tokens](https://docs.hatchet.run/v1/api-tokens)). There are two token levels: **unrestricted**, which workers need and which "bypasses tenant member role checks in the REST API", and read-only. **No trigger-only or worker-only scope.**
- Priority "only affects multiple runs of a _single_ workflow" ([priority](https://docs.hatchet.run/v1/priority)). Concurrency is scoped to a workflow, or shared by name across workflows (engine ≥0.106.0). All of this is inside one tenant.

| Option                                                | Isolation                                                                                                                                                                                                                                                                                            | Shared-service priority / fair share                                                                                                                                                                                        |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tenant per Instance                                   | API-level. Tenant scoping is still being hardened: v0.106.5 "Satisfied durable event lookups are filtered by tenant", v0.110.5 workflow-version lookups scoped to tenant, v0.114.2 token JWT subject must match tenant ([platform changelog](https://docs.hatchet.run/reference/changelog/platform)) | **Lost.** Each Python service runs one worker per tenant (N tokens). Slots are per worker, so total concurrency is N × slots. No cross-tenant priority or fairness, which is the reason to use Hatchet for Shared services. |
| One tenant, Instance in input / `additional_metadata` | **None between Instances.** Every Instance token can list, read, cancel and replay all runs and payloads                                                                                                                                                                                             | Works: `GROUP_ROUND_ROBIN` on `input.instance`, priority inside one workflow per service (#125)                                                                                                                             |

Where payloads live: "PostgreSQL is the source of truth … inputs/outputs, retries" ([architecture](https://docs.hatchet.run/v1/architecture-and-guarantees)). Run retention defaults to 30 days (`SERVER_LIMITS_DEFAULT_TENANT_RETENTION_PERIOD=720h`, [data retention](https://docs.hatchet.run/self-hosting/data-retention)). The payload store has an inline TTL of 2 days plus an "external cutover" offload; its backend is not documented ([config](https://docs.hatchet.run/self-hosting/configuration-options)). Encryption keysets exist, but the docs do not say payloads are encrypted at rest. Readers: the engine DB role, Postgres superuser, DB backups, any tenant member in the dashboard (per-member payload visibility restriction since v0.105.2), and any unrestricted token of the tenant.

What that means for our data:

- **Instance-internal queues:** payloads are already only ids and storage keys (table above). Bulk-email bodies, submissions and P12s stay in the Instance DB/S3. So the payload exposure is small, but the namespace leak above is real.
- **Shared-service work:** the inputs _are_ the content: DOCX/PDF bytes, and for `/v1/sign-pdf` the **P12 plus its password**. Through Hatchet these would sit in one cross-conference Postgres for up to 30 days unless every job is rewritten as a claim check (MinIO key or presigned URL), and the P12 password would still be in the payload. Today they exist only in RAM for one request.

## 3. Version skew

- No published compatibility matrix or policy. Docs and changelogs show:
  - Migrations run automatically on engine start. Downgrade means restoring a snapshot or running down-migrations, and "Both … will result in data loss and some downtime" ([upgrading](https://docs.hatchet.run/self-hosting/upgrading-downgrading)).
  - Newer SDK features silently need a newer engine: `slotCost` "on older engines it has no effect" (TS and Py). `streams.publish` batching "Requires an engine that serves `V1Streams/PublishBatch`; older engines reject it as unimplemented", followed by a fallback patch. Second-level cron is "only supported on new engine versions".
  - Old SDKs keep being served (v0.114.2 registers the DAG operator "for workflows put by very old SDKs"), but the v0 API was removed in v0.74.1 (2025-12-31).
  - The Python SDK warns on init "if the SDK version is not compatible with the tenant (engine) version" (1.12.0, 2025-06-06); the rule it applies is not published.
- Rule that follows: **engine first, then SDKs**, which matches the map's "suberus-common before Instances". Instances on mixed app versions are fine as long as no Instance uses an SDK feature newer than the engine.
- **Skew risk the map does not cover:** in one tenant, two Instances on different app versions register the **same workflow name** with different definitions (concurrency, timeouts, retries), and the last registration wins. Instance namespaces avoid this for internal queues. For Shared-service workflows the Python worker owns the definition, and TS only triggers through a stub, so the definition lives in one place.
- Pace: about 14 engine minors in 10 weeks, pre-1.0, `btree_gist` needed since v0.87.6. Staying near current means a snapshot-and-upgrade on jack roughly monthly. Each upgrade takes all Instances' queues down together.

## 4. Shared services as Python workers

Answered in #125, confirmed against current docs. One addition per bullet:

- **Priority `interactive` > `batch`:** works only if both classes are runs of the **same workflow** per service. Python declares one workflow per endpoint group and the class becomes the run priority (1–3).
- **Fair share:** `GROUP_ROUND_ROBIN` with key `input.instance` (or metadata), `maxRuns` = service slots. Subject to #4778 and #5254 above. Only possible in one tenant (§2).
- **Wait from TS:** `run()` resolves with the result. `runNoWait()` plus `runRef(id)` gives the result later ([running tasks](https://docs.hatchet.run/v1/running-your-task)). The TS `/core` client polls `GetRunDetails` with 250 ms→5 s backoff (CHANGELOG 1.46.x). The docs do not describe a client-side wait timeout, so our 30/60 s interactive deadlines would need our own `AbortSignal`/race.
- **Payload limit:** engine `SERVER_GRPC_MAX_MSG_SIZE` default 4 194 304. Client `grpc_max_{recv,send}_message_length` default 4 MB. Both can be raised, but the architecture page lists "payloads over 1MB" as a bottleneck, and every byte is persisted (§2). An IDML export or signed PDF over a few MB needs a claim check. That means Shared services get per-Instance MinIO credentials or presigned URLs both ways, and stop being stateless.

## 6. Local dev and E2E impact

- Local dev gets one more container (`hatchet-lite` + its DB or a DB in the dev Postgres) and a token in `.env`. Alternatively, embedded mode: TS and Python since v0.105.2, "early beta". It downloads the `hatchet-embedded` sidecar binary at runtime, with bundled Postgres by default or `databaseUrl`. Its auto-managed encryption keys are "convenient for development" ([embedded](https://docs.hatchet.run/v1/embedded)).
- E2E today gets queue isolation for free from the per-worker DB. With Hatchet:
  - Per-worker `namespace` (e.g. `e2e_w${i}_`), passed through `envFor(i)`.
  - Engine state **does not reset** with `global-setup`'s DB recreation. Leftover scheduled or retrying runs from a previous run fire into the fresh DB under the same namespace. That needs a per-run namespace suffix or an engine wipe.
  - "Two instances started from the same working directory cannot share the bundled Postgres data directory", and engines "must not apply migrations at the same time". So use one engine for all E2E workers, not one per worker.
  - CI (`ci.yml`, E2E deferred) would need the engine as a service too.
- The map says local compose and E2E stay unchanged. Replacing pg-boss entirely contradicts that. Hatchet only for Shared-service work does not, as long as local and E2E keep calling the sidecars over HTTP. That means two code paths, one per environment.

## 7. Migration path and blast radius

Migration (if ever done for Instance-internal queues):

1. Ship the Hatchet producer behind a flag. Keep pg-boss workers registered so in-flight and scheduled pg-boss jobs drain. Nothing reads pg-boss job ids, so no id mapping.
2. Scheduled work need not be copied out of `pgboss.job`. App rows in status `SCHEDULED` (`email_campaign`, `announcement`) carry `scheduledAt`. A one-off reconcile re-schedules them in Hatchet. Duplicates are harmless because the worker claim matches `scheduledAt`, and only one of the two jobs wins the claim. The same reconcile doubles as disaster recovery if the Hatchet DB is lost.
3. In-flight `document-generate`/`extraction`: let them drain (≤ `expireInSeconds` × retries, ~30 min worst case). `PENDING` documents without a job can be re-enqueued by id, like `resignSignedDocuments` already does.
4. After a drain window, remove pg-boss and drop the `pgboss` schema per Instance.

Blast radius if the engine is down:

- **Today:** pg-boss down means that Instance's DB is down, and that Instance is down anyway. All Instance DBs share `srv-shared-postgres`, so Postgres is already a host-wide single point of failure. The engine would add a **second** one (container + gRPC), plus its upgrades.
- **With Hatchet for all work:** for all 4 Instances at once, every enqueue rejects:
  - Campaigns and announcements roll back to DRAFT with an error.
  - Extraction upload errors after the file is stored.
  - Bulk document generation half-enqueues.
  - Scheduled sends slip until the engine is back, then fire once ("Time spent down does not create extra runs").
  - Running workers lose their stream and reconnect.
- **With Hatchet for Shared-service work:** interactive diff/IDML/cert calls fail on every Instance, and batch work retries via pg-boss. Under #125's baseline the same outage class is "Shared service container down", with no extra component.

## Could not verify

- Hatchet RAM/CPU and Postgres connection use **under load**. Only measured idle. Not tried with `DATABASE_MAX_CONNS` capped to ~10.
- Whether Postgres-only (`SERVER_MSGQUEUE_KIND=postgres`) is recommended for production. Docs still don't say (same gap as #125).
- Whether payloads are encrypted at rest, and which backend the "external" payload store uses in self-hosted mode (changelog mentions S3; config docs don't).
- Fixed-delay retries (only exponential `backoff` is documented) and per-run `executionTimeout` override.
- Client-side behaviour when the engine is unreachable at trigger time (retrier settings exist, `HATCHET_CLIENT_RETRIER_*`; no documented failure semantics).
- Hatchet TS SDK inside the nitro/rolldown server bundle (gRPC deps, duplicated module copies). Not built.
- Whether one Python process can run several workers with different tenant tokens. Not documented, and moot if one tenant is chosen.
- Status of open bugs #4778 and #5254 on v0.119.2. Both still open on 2026-11-08; the affected-version ranges in the reports stop at v0.104.7 / v0.112.12.
