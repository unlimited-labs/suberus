# Research: shared job broker for Shared services

Issue: unlimited-labs/suberus#125 (map #124). Date: 2026-11-08. Branch `research/shared-job-broker`, never merged.

## TL;DR

- **(a) A shared broker does not beat the in-service admission queue for this workload.** All batch work already sits in a durable, retrying pg-boss queue inside each Instance, with `localConcurrency` 1–2, so cross-Instance load on a Shared service is bounded by construction (worst case ~8–12 concurrent calls per service). A broker would add a second durable queue in front of the first, a new stateful component, a result channel for MB-sized bytes (MinIO + credentials in now-stateless services), and it would persist signing P12s + passwords at rest in a cross-Instance store. What it buys (global fairness across replicas, queue survives service restart) does not matter at 1 replica per service on one host.
- **(b) If a broker is ever needed** (multi-host, several replicas per service, durable interactive jobs): Hatchet > DBOS > pg-boss (dedicated DB + `@pg-boss/proxy`) > Temporal > BullMQ > Procrastinate > pgmq. Only Hatchet and Temporal ship real round-robin fair share per key; only Hatchet does it with low ops and an MIT licence.
- **(c) Recommendation:** baseline. One ASGI admission middleware shared by the 3 services: per-service slot limit, two classes (`interactive` waits with a deadline, `batch` gets `503 + Retry-After` when it can't start soon), round-robin across `X-Suberus-Instance` keys within a class. Instance side: send the two headers, treat 503 as retryable, give pg-boss jobs `retryBackoff`. Bytes keep travelling in the HTTP body. Revisit Hatchet only if a trigger in "When to revisit" fires.

Correction to the map's wording: PDF _signing_ of generated documents is batch (#5), not interactive. Interactive docx-api work is diff, IDML, and cert gen/inspect/verify. docx-api's `/v1/ast` and `/v1/omml` (editor preview) have no caller in `src/` on `master` yet.

Current service-side concurrency control:

- docx-api: none. Sync routes run in Starlette's threadpool; AnyIO's default thread limiter is 40 ([AnyIO threads docs](https://anyio.readthedocs.io/en/stable/threads.html)), so up to 40 LibreOffice/pandoc jobs can start at once.
- pdf-api: a module-level `asyncio.Lock` serialises docling conversions (`services/pdf-api/main.py`, `_convert_lock`). This is already an admission queue with concurrency 1, but FIFO with no fairness or priority, and no early 503. Waiters just sit until the caller's 120 s timeout fires.
- planner: none (sync k-means).

Worst-case concurrent calls with 4 Instances (sum of `localConcurrency`, one app process per Instance): docx-api 8 batch + interactive, pdf-api 12 batch queued behind one lock, planner 4. The real failure mode today is that pdf-api queue: 12 docling jobs of tens of seconds each behind one lock means timeouts and blind pg-boss retries. Fair-queue admission plus 503 fixes exactly that.

Stack preference (`dev-docs/STACK.md`): Postgres + pg-boss already in every Instance. Shared services are "in-stack microservices (Python/FastAPI)" with `/v1` versioning. No broker is listed.

## (a) Shared broker vs baseline admission queue

Baseline as specified in #125: each service limits its own concurrency, keeps an in-memory fair queue keyed by an Instance header, answers `503 + Retry-After` (RFC 9110 §15.6.4 lets a 503 carry `Retry-After`), and Instance pg-boss retries.

| Concern                                 | Baseline (in-service admission)                                                                                                                                                                                                                                                                                                          | Shared broker                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Durability of batch work                | Already durable: pg-boss in each Instance DB, retries, expiry (table above)                                                                                                                                                                                                                                                              | Duplicates it. Instance job → broker job, two retry policies to reconcile                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Interactive call                        | Unchanged HTTP request/response; request waits in the priority queue up to a deadline                                                                                                                                                                                                                                                    | Becomes enqueue + wait (poll/LISTEN/SDK `run()`); adds latency and a second timeout                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Large binary results (MB PDF/DOCX/IDML) | Unchanged: response body                                                                                                                                                                                                                                                                                                                 | Needs a claim-check store. Temporal caps payloads at 2 MB by default ([docs](https://docs.temporal.io/troubleshooting/blob-size-limit-error)), Hatchet gRPC at 4 MiB (`SERVER_GRPC_MAX_MSG_SIZE`, [config](https://docs.hatchet.run/self-hosting/configuration-options)), DBOS portable JSON has no bytes type ([portable workflows](https://docs.dbos.dev/explanations/portable-workflows)). So results would go to MinIO, and stateless services would need per-Instance bucket credentials or presigned URLs both ways |
| Secrets                                 | P12 + password live only in the request, in RAM                                                                                                                                                                                                                                                                                          | Persisted in the broker's tables or payload store, shared by all Instances, unless every job is rewritten to pass a MinIO reference                                                                                                                                                                                                                                                                                                                                                                                       |

| Fair share                              | Exact within one replica (round-robin over keys). Per replica if scaled out                                                                                                                                                                                                                                                              | Global across replicas                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Survives service restart                | In-memory queue lost. Interactive caller gets a connection error and retries. Batch: pg-boss retries                                                                                                                                                                                                                                     | Queue survives. But an interactive caller has usually timed out anyway                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| New infra                               | None                                                                                                                                                                                                                                                                                                                                     | New service and/or DB, credentials, backups, upgrades, on a host shared with other projects                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Observability                           | Expose queue depth per class/Instance on the service (e.g. `GET /` health JSON)                                                                                                                                                                                                                                                          | Broker UI or dashboard (Hatchet, pg-boss dashboard)                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

Verdict: the baseline wins on every axis that matters at the current scale (one host, 1 replica per service, 4 Instances, bounded batch fan-in). The broker's advantages are real but conditional: global fairness across several replicas or hosts, and durable interactive jobs. The evidence does **not** support the user's preference for a shared broker today.

Weak spots of the baseline, and their fixes:

- pg-boss has no "retry at Retry-After": retries use `retryDelay` / `retryBackoff` / `retryDelayMax` ([pg-boss jobs API](https://pgboss.io/api/jobs), 12.38.1). Fix: raise `retryLimit` for these queues and turn on `retryBackoff`. The Retry-After value is a hint only.
- A 503 retry consumes a pg-boss attempt. Fix: count 503 separately, or set a higher `retryLimit`. Cheap.
- Fair share is per replica. Acceptable while each service runs 1 replica. pdf-api scales by adding in-process slots once docling is safe to run concurrently, otherwise by replicas.

Ranking if a broker is required: **1 Hatchet** (only low-ops option with true per-key round-robin, priority and request/response in both SDKs; caveat: priority only within one workflow). **2 DBOS** (no new service, priority + per-key caps; the cross-language path is 7 months old). **3 pg-boss dedicated DB** (stack-native producer, but Python goes through a young HTTP proxy, and the per-group cap gives no RR). **4 Temporal** (best fairness semantics, disproportionate ops). **5 BullMQ** (fairness is paid, TS-only). **6 Procrastinate**, **7 pgmq** (you'd rebuild the baseline in SQL).

Other options seen, not pursued: River (Go workers), graphile-worker (Node only), pgque (PgQ-based, Python client only).

## (c) Recommendation

Adopt the baseline. Concretely:

1. **One ASGI middleware**, copied into the 3 services or shared as a tiny local package: `slots` per service (env), two classes from `X-Suberus-Priority: interactive|batch` (default `batch`), round-robin over `X-Suberus-Instance` within a class, interactive always admitted first.
   - Interactive: wait up to a deadline below the caller's timeout, then 503.
   - Batch: 503 + `Retry-After` when it can't start within a few seconds or the queue is over its depth limit.
   - Health stays unqueued and reports per-class/per-Instance depth (the map's observability item).
2. **pdf-api:** replace `_convert_lock` with the middleware (slots=1 keeps the serialisation, adds fairness and early 503).
3. **docx-api:** caps LibreOffice/pandoc fan-out, which today is bounded only by AnyIO's 40 threads.
4. **Instance:** `sidecar-http.ts` sends both headers (Instance id from env, class per call site, table above). Map 503 to a retryable error. On queues 5–8, set `retryBackoff: true` and raise `retryLimit`.
5. **No MinIO round-trip, no new infra, no secrets at rest.**

When to revisit (then pick Hatchet, Postgres-backed, its own DB in shared Postgres): Shared services spread over more than one host, or need more than 1 replica with global fairness; or a requirement that interactive jobs survive a service restart; or more Instances than the bounded fan-in can absorb (watch p95 queue wait in the health output).
